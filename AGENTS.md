# AGENTS.md — Развозка учеников

## О проекте

Сайт для регистрации детей на развозку.
Описание для людей — в `README.md`, требования к новым функциям — в папке `specs/`.

Целевая структура: `index.html` — разметка, `styles.css` — оформление, `script.js` — логика.
Сейчас страница находится в `public/index.html` и содержит встроенные CSS и JavaScript; в проекте также есть конфигурация и серверные файлы Supabase. Эти инструкции задают правила дальнейшей работы, а не означают, что переход на локальное хранение уже выполнен. Не переносить файлы и не переделывать существующие функции без отдельного запроса.

## Правила

- Только HTML, CSS и JavaScript в этой папке.
- Данные храни в браузере (localStorage).
- Кнопки и поля не меньше 44px, страница работает на телефоне шириной 375px.
- Делай только то, о чём попросили. Работающие функции не ломай.
- После тестов обязательно делать гит-коммит.
- Не добавлять npm, библиотеки, сборку и внешние ресурсы.
- По прямому запросу пользователя разрешён OpenStreetMap: общая карта Астаны, выбор родителем координат здания и открытие этой метки организатором, ручной переход к поиску улицы/здания. Не передавать ему ФИО, телефоны, PIN и списки пассажиров; не добавлять npm и библиотеки ради карты.
- Новые функции не должны отправлять данные в интернет. Существующие интеграции не менять без отдельного запроса.
- Новые подписи писать на русском языке, коротко и понятно; существующую казахскую локализацию сохранять.
- Для примеров и проверок использовать только вымышленные данные, без реальных данных детей и родителей.
- Для доставок в Астану формировать группы только внутри одного рейса (дата, направление, время): до 7 детей по близким координатам и гексам с ориентиром 3–4 улицы и допуском ±2 улицы по запросу пользователя (specs/009-avtogruppy-geksy.md). Без адресного справочника не утверждать, что число улиц определено; прежний предел четырёх улиц сохраняется только для ручной сборки. Остаток — отдельная неполная группа. Близость определять по конкретным зданиям, а не только названию улицы или номеру гекса; не терять и не дублировать записи.
- Деньги показывать в тенге, например `5 500 ₸`; даты — `ДД.ММ.ГГГГ`, время — `ЧЧ:ММ` по Астане (UTC+5).
- Не публиковать сайт и не выполнять удалённые изменения без прямого запроса.

- Для собственного адреса требовать подтверждённую родителем метку у здания. Координаты сохраняет сервер и получает организатор; не называть родительскую метку проверенным адресом. См. specs/004-tochka-roditelya-na-karte.md. Новые записи — только машины, старые записи другого транспорта остаются архивными.

## Сверка записей и готовые списки

- Реализовывать проверку приложением на сервере: до дедлайна — предварительная сверка адресов зданий и состава; непосредственно перед подтверждением и выгрузкой — повторное чтение актуальной версии записей. Наличие AGENTS.md само по себе не запускает фоновые задачи.
- Исключать отменённые записи, переносить изменившие рейс записи в правильный рейс. Изменение адреса, времени, состава, общей точки или дедлайна делает затронутые группы устаревшими. Не выдавать старую выгрузку за актуальную при ошибке связи.
- Проверять реальное здание по согласованному источнику карты/адресов; хранить источник, результат и время проверки. Не подменять неизвестный адрес центром улицы. «Не найдено» и «Не удалось проверить» — разные результаты.
- Гекс служит зоной ближайших участков 3–4 улиц, но группировка дополнительно учитывает координаты конкретного здания. Геометрическая ячейка не гарантирует фиксированное число улиц. По одному названию улицы детей не объединять.
- Общие точки добавляет, изменяет и отключает только организатор; родители выбирают активную точку из выпадающего списка либо свой адрес. Адрес, координаты и цена выбранной точки проверяются сервером.
- Организатор настраивает дедлайн конкретного рейса. Родителям показывать полные дату и время закрытия по Астане; одинаковый дедлайн действует в форме, SQL и обработчике отправки. Повторное открытие рейса инвалидирует готовые группы.
- Основные колонки готового списка и XLSX: группа, ФИО, адрес здания/общей точки, телефон родителя, статус. Состояние записи и результат проверки адреса хранить раздельно.
- Корректный телефон может открывать WhatsApp по нажатию; не отправлять сообщения автоматически. Не делать пользовательские значения формулами XLSX.
- Эти правила — требования к дальнейшей реализации по specs/003-deadline-tochki-spiski.md. Не сообщать, что проверки, общие точки и настраиваемые дедлайны уже работают, пока код не реализован и не проверен.

## Записи после дедлайна и водители

- После дедлайна родитель не может изменить или отменить запись; проверку выполнять на сервере. Только организатор с проверенными сервером правами может изменить или отменить запись после дедлайна.
- В кабинете организатора вести список водителей: имя, телефон и номер Kaspi. Не добавлять реальные данные в примеры и тесты; сведения доступны только уполномоченным пользователям.
- После дедлайна организатор группирует активные записи по правилам близости, назначает водителя каждой группе и явно публикует результат. До публикации родители не видят назначение водителя.
- После публикации родитель видит сведения назначенного водителя только для своих записей. Родителю показывать имя, телефон и номер Kaspi назначенного водителя для оплаты развозки; не раскрывать другие записи, группы и контактные данные.
- При отмене, переносе или изменении адреса, времени, состава, водителя или дедлайна обеспечить актуальность групп и публикации; не показывать устаревшее назначение как подтверждённое. Правила описывают требуемую функцию, а не подтверждают её реализацию. См. specs/007-voditeli-publikaciya.md.

- Автогруппы определять на сервере по координатам своей и соседних ячеек; гексы не подтверждают существование здания. Не требовать ручного ввода улицы для каждой записи с координатами. Неизвестные координаты — отдельный список уточнения. Не смешивать рейсы и не менять существующие группы при повторном запуске.

## Новая функция

- Каждую новую функцию начинать с файла `specs/NNN-nazvanie.md`. `NNN` — следующий свободный номер: `001`, `002`, `003`. Название — латиницей через дефис.
- Разделы файла: «Для кого и зачем», «Что должно быть», «Примеры», «Ограничения», «Готово, когда».
- Пока пользователь не написал «делай», код новой функции не писать.
- Когда функция готова, обновить `README.md`: что умеет страница и как проверить.

## Как проверить

- Открыть текущую страницу `public/index.html` двойным щелчком. После отдельно согласованного переноса в корень — открывать `index.html`.
- Проверить сценарии из раздела «Готово, когда» соответствующей спецификации.
- Для функции с локальным сохранением: ввести вымышленную запись → сохранить → увидеть её в списке → нажать F5 → убедиться, что запись осталась. Это критерий для будущей реализации, а не утверждение о текущей работе сайта.
- На ширине 375px нет горизонтальной прокрутки; кнопки и поля имеют ширину и высоту не меньше 44px, текст читается, фокус виден.
- Проверять на вымышленных данных, без обращения к рабочей базе и без отправки сообщений.
- После выполненных проверок сделать гит-коммит только своих изменений. Не включать чужие правки и секреты, не выполнять push без запроса.
